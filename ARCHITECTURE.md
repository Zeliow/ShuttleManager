# Архитектура проекта Shuttle Manager

Данный документ описывает архитектуру системы Shuttle Manager — кроссплатформенного приложения (WMS/WCS) для управления роботизированными складскими шаттлами. Документ предназначен для последующего использования в качестве контекста при генерации UML-диаграмм и написании инженерной документации.

## 1. Общая архитектура и сервисы (Deployment & Component Context)

### 1.1 Архитектурный стиль и платформы
Проект построен на базе **.NET MAUI Blazor Hybrid** (целевой фреймворк .NET 10.0), что позволяет создать единую кодовую базу для нативного приложения на платформах Windows и Android.

*   **MAUI Host (Нативный слой):** Проект `ShuttleManager` отвечает за жизненный цикл нативного приложения, системные интеграции (например, файловую систему) и предоставляет `BlazorWebView` — контейнер для рендеринга пользовательского интерфейса.
*   **Blazor Web-слой (UI и логика):** Проект `ShuttleManager.Shared` (Razor Class Library) содержит всю бизнес-логику, компоненты интерфейса (HTML/CSS без тяжелых UI-библиотек) и сервисы связи с оборудованием.

### 1.2 Ключевые сервисы и Dependency Injection
В приложении используется паттерн Dependency Injection (DI) для предоставления инфраструктурных и бизнес-сервисов:

*   **`IShuttleHubClientService` / `ShuttleHubClientService` (Singleton/Scoped):** Главный сервис управления TCP-соединениями. Отвечает за сканирование сети (`ScanNetworkAsync`), поддержание подключений (`ConnectToShuttleAsync`), маршрутизацию входящих и исходящих сообщений. Реализует паттерн **Observer** через события `LogReceived`, `Connected`, `Disconnected`, на которые подписываются UI-компоненты.
*   **`IShuttleProtocolHandler`:** Абстракция для обработки протоколов обмена. В коде реализованы две версии протокола:
    *   `BinaryProtocolHandler`: Для нового бинарного V2 протокола, который парсит байтовые пакеты со структурой `FrameHeader` и проверкой CRC16 CCITT.
    *   `LegacyProtocolHandler`: Для устаревшего текстового протокола.
*   **`IOtaUpdateService`:** Отвечает за процесс обновления прошивки (OTA) шаттла (загрузка файлов, трекинг прогресса).
*   **Служебные сервисы:** `IFilePickerService` (выбор файлов для прошивки), `IWebBrowserService` (вызов внутреннего/внешнего браузера для конфигурации шаттлов).

## 2. Концепция данных и расхождения (Class Context)

Система разделяет данные на три основных слоя для изоляции логики работы с сетью от пользовательского интерфейса:

### 2.1 Транспортные модели / DTO (Слой сети)
Определены в файле `Protocol.cs` (пространство имен `ShuttleManager.Shared.Models.Protocol`).
Используются структуры (`struct`) с точным расположением в памяти (`[StructLayout(LayoutKind.Sequential, Pack = 1)]`) для быстрой сериализации и десериализации бинарных данных, получаемых из `TCPClient` потока.
*   *Примеры:* `FrameHeader`, `TelemetryPacket`, `SensorPacket`, `StatsPacket`, `ConfigPacket`, `SimpleCmdPacket`.
Сырые байты читаются через `MemoryMarshal.Read<T>()` или `BinaryPrimitives` и конвертируются в наследников `ShuttleMessageBase` (например, `TelemetryMessage`, `SensorMessage`), чтобы передать их выше по иерархии через callback'и.

### 2.2 Доменные модели (Слой бизнес-логики)
Основная сущность, представляющая состояние конкретного подключенного робота — класс `Shuttle` (в `ShuttleManager.Shared.Models.Shuttle.cs`).
*   Аккумулирует в себе все агрегированные метрики: напряжение батареи (`BatteryVoltage`), текущий статус (`CurrentStatus`), наличие ошибок (`ErrorCode`), счетчики операций (`LoadCounter`), расстояния с датчиков (`ForwardDistance`) и логи работы (`_terminalMessages`).
*   В классе реализована потокобезопасность через объект блокировки `_lock` при модификации коллекций (например, `AddTerminalMessage`, `GetTerminalMessages`).

### 2.3 Модели представления (UI State)
Состояние биндится напрямую в компонентах (например, в `ShuttleHubControlComponent.razor.cs`). Когда из фонового потока (от `ShuttleHubClientService`) поступает новое сообщение (событие `LogReceived`), вызывается метод `ProcessLogAsync`.
Здесь данные из DTO-сообщения (например, `TelemetryMessage`) перекладываются в доменную модель `Shuttle` через методы обновления (например, `UpdateTelemetry(tm.Data)`).

**Синхронизация потоков:** Так как чтение из TCP-сокета происходит в фоновом `Task` (в `ReceiveLoopAsync`), а обновление UI должно выполняться в основном (UI) потоке, используется метод Blazor `InvokeAsync(StateHasChanged)`. Запись логов в файлы происходит асинхронно в фоне с использованием `SemaphoreSlim` (`_logLock`), чтобы не блокировать UI-поток при высоких частотах телеметрии.

## 3. Динамика взаимодействия (Sequence Context)

**Сценарий: Отправка команды движения на шаттл (вперёд) и получение подтверждения (ACK)**

1.  **UI Event:** Пользователь кликает кнопку "Проезд расстояния вперёд" в HTML интерфейсе компонента `ShuttleHubControlComponent.razor`.
2.  **Razor Code-Behind:** Вызывается C#-метод `SendMoveForwardShuttleCommand()`, который в свою очередь вызывает `SendCommand(ShuttleCommand.MoveDistanceForward, ...)` внутри компонента. Включается флаг блокировки интерфейса `_isCommandInProgress = true`.
3.  **Передача в Сервис:** Компонент вызывает `HubClientService.SendCommandAsync(ip, cmd, arg1, arg2)`.
4.  **Слой протокола:** `ShuttleHubClientService` находит нужный `ShuttleConnection` и делегирует вызов в `BinaryProtocolHandler.SendCommandAsync`.
5.  **Маппинг и формирование DTO:** `BinaryCommandMapper` транслирует `ShuttleCommand.MoveDistanceForward` в байтовый код `CmdType.CMD_MOVE_DIST_F`. Создается структура `ParamCmdPacket` (тип команды и аргумент-дистанция).
6.  **Упаковка в пакет (Framing):** Метод `SendPacketAsync` упаковывает `ParamCmdPacket` в общий фрейм:
    *   Добавляются стартовые синхро-байты (`0xBB`, `0xCC`), идентификатор сообщения `MsgID.MSG_CMD_WITH_ARG`, номер последовательности `seq` и длина.
    *   Считается контрольная сумма (CRC16 CCITT) и добавляется в конец пакета.
7.  **Отправка и ожидание ACK:** Байт-массив асинхронно отправляется в сокет (`connection.Transport.WriteAsync`). Создается `TaskCompletionSource<bool>`, который складывается в словарь `_ackWaiters` по ключу `seq`, и метод начинает асинхронное ожидание (с таймаутом).
8.  **Получение ACK (Фоновый поток):** `ReceiveLoopAsync` в `ShuttleHubClientService` вычитывает байты из сокета, `BinaryProtocolHandler` парсит пакет, видит `MsgID.MSG_ACK` и вызывает `HandleAck`.
9.  **Завершение ожидания:** Метод извлекает из `_ackWaiters` ожидающий таск по полученному `RefSeq` и делает `TrySetResult(true)`. Ожидание в шаге 7 завершается успешно.
10. **Обновление UI:** Управление возвращается в `ShuttleHubControlComponent`, блок `finally` снимает флаг `_isCommandInProgress = false` и вызывает `StateHasChanged()`, возвращая UI в активное состояние.

## 4. Бизнес-процессы (Activity & Use Case Context)

Система охватывает процессы двух основных акторов.

### Актор 1: Оператор WMS (Пользователь)
Система предоставляет оператору интерфейс диспетчеризации для управления и конфигурации:
*   **Сетевое обнаружение:** Сканирование подсетей TCP/IP для автоматического поиска активных шаттлов (`ScanNetworkAsync`).
*   **Мониторинг телеметрии:** Получение в реальном времени статусов батареи, текущей позиции в канале, статуса подъемника (`IsLifterUp`, `IsLifterDown`), температурных и ToF датчиков (датчиков расстояния до препятствий и паллет).
*   **Прямое управление движением и грузом:** Оператор может отправлять ручные команды: движение по осям (`Left`, `Right`), мануальные подъемы/спуски (`LiftUp`, `LiftDown`), команды на загрузку (`Load`), выгрузку (`Unload`) и уплотнение паллет (`SealForward`, `SealBackward`).
*   **Экстренное управление:** Остановка шаттла (`Stop`), сброс аппаратных и программных ошибок (`Reset`, `SystemReset`).
*   **Конфигурация:** Изменение критических параметров работы: межпаллетное расстояние, максимальная скорость, длина шаттла, уровень защиты разряда батареи, настройка режимов FIFO/LIFO (методы `SendConfigCommand`).
*   **Оперирование прошивками:** Запуск процесса обновления микрокода (OTA Update) контроллера с загрузкой файла из файловой системы устройства оператора.

### Актор 2: Роботизированный Шаттл (Оборудование)
С точки зрения системы, шаттл — это автономный агент, выступающий источником потоковых данных и исполнителем команд:
*   **Трансляция состояния (Push):** Периодическая и событийная отправка метрик (MSG_HEARTBEAT), данных с сенсоров (MSG_SENSORS) и статистики (MSG_STATS).
*   **Логирование на уровне контроллера:** Отправка сырых логов (MSG_LOG) с градацией важности (INFO, WARN, ERROR, DEBUG), которые система логирует на диск в фоновом режиме для дальнейшей отладки поведения робота.
*   **Исполнение задач (Actuation):** Парсинг бинарных команд на перемещение или изменение режимов работы с последующей отправкой подтверждений (ACK), что позволяет WMS-системе строить надежную конечную-автоматную логику (State Machine).
